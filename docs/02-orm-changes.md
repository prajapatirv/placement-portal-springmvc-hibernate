# Task 3: ORM (Hibernate / JPA) Mapping and Changes

Stack as built and verified: Java 21, Spring Boot 3.5.16, Hibernate ORM 6.6.x, Spring Data JPA, Flyway, PostgreSQL / H2.

## 1. Mapping summary

| Entity | Annotations that matter | Teaching point |
| --- | --- | --- |
| `Company` | `@OneToMany(mappedBy="company")` | inverse side, no column of its own |
| `JobPosting` | `@ManyToOne(fetch=LAZY, optional=false) @JoinColumn(name="company_id")`, `@Enumerated(STRING)` | owning side, LAZY on purpose; `isOpenOn()` business rule on the entity |
| `Student` | `@Column(unique=true)` email | unique constraint mirrors the DB |
| `Application` | two LAZY `@ManyToOne`, `@UniqueConstraint`, `@Version` | association entity, optimistic locking |

Common rules: `@GeneratedValue(IDENTITY)` (matches `generated by default as identity`), `protected` no-arg constructor for JPA, enums stored as strings, `BigDecimal` for money/CGPA, no cascades, no `EAGER` anywhere.

## 2. What was changed or added compared with the demo guide

| # | Change | Why |
| --- | --- | --- |
| 1 | H2 URL gets `DATABASE_TO_LOWER=TRUE` | **Found by running it.** Flyway creates a quoted lowercase schema `app`, Hibernate looks for unquoted `APP` on H2, so `ddl-auto=validate` failed with "missing table [application]". Lower-casing makes both agree. PostgreSQL was never affected. |
| 2 | `flyway-database-postgresql` dependency | required by newer Flyway to talk to PostgreSQL |
| 3 | Setters, convenience constructors, `nullable=false` on every mandatory column | needed for CRUD (update/delete) and so the mapping documents the DB constraints |
| 4 | `ConflictException` base class; `DuplicateApplicationException`, `JobClosedException` extend it | one handler gives a 409 page with a safe message; forms show the message inline |
| 5 | `findAllWithDetails` ordered by `appliedAt desc, id desc` | stable order when seed rows share a timestamp |
| 6 | `findWithDetailsById` on `ApplicationRepository` | status form loads one row in one query |
| 7 | `CompanyRepository.findAllWithJobCount()` (JPQL constructor expression, `group by`) | showing a posting count per company with `postings.size()` or `countByCompanyId` per row would create a **new N+1** on the company page |
| 8 | `JobRepository.findAllBy(Pageable)` + `@EntityGraph(attributePaths="company")` | paged admin list; a to-one fetch is safe with paging |
| 9 | Interface projection `JobSummary` | two-column select (L6) |
| 10 | `application-batch.properties`: `hibernate.default_batch_fetch_size=20` | the "softer" N+1 fix as a **profile toggle** instead of editing entities, so the 26-statement demo and the 4-statement demo coexist. Measured: 26 -> 4 |
| 11 | `spring.mvc.format.date=iso` | `<input type="date">` posts `2026-12-01`; default locale parsing would reject it |
| 12 | Record forms (`CompanyForm`, `JobForm`, ...) separate from entities and from view records | controllers never bind to or expose entities |
| 13 | `ApplicationRow` carries `id`, `appliedAt`, `version` | buttons and the hidden version field need them |
| 14 | Apply, shortlist, bulk shortlist, change status (version check), withdraw in `ApplicationService` | L1 to L5 in one service, all `@Transactional` at the service layer |

## 3. Fetching decisions

| Place | Strategy | Result |
| --- | --- | --- |
| Applications page, slow | plain `findAll()`, LAZY proxies | 26 statements |
| Applications page, fast | `join fetch student, job, job.company` | 1 statement |
| Open jobs, city filter | `join fetch company` | 1 statement |
| Job detail | `findWithCompanyById` (join fetch) | 1 statement |
| Manage jobs (paged) | `@EntityGraph` | 1 data + 1 count |
| Company list | grouped constructor query | 1 statement |
| Batch profile | `default_batch_fetch_size=20` | 4 statements |

Rule: never fix N+1 by switching to EAGER.

## 4. Transactions and concurrency

* `@Transactional` only on the service layer; reads use `readOnly = true`.
* **Dirty checking:** `shortlist()` and every `update(...)` change a managed entity and never call `save()`; Hibernate writes `update ... where id=? and version=?` at commit.
* **Rollback:** `bulkShortlist([a, b, 9999])` throws, so a and b are not changed (`ApplicationServiceTest`).
* **Optimistic locking:** `@Version` plus a hidden `version` field in the form; a stale form raises `ObjectOptimisticLockingFailureException` -> 409 page.
* **Two guards against double apply:** `existsByStudentIdAndJobId` (friendly message) and unique constraint `uq_application` (the real guard under a race).
* `open-in-view=false`: lazy loading in views is deliberately impossible, so services return DTOs.

## 4b. Configuration that exposes Hibernate

```properties
logging.level.org.hibernate.SQL=DEBUG
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.properties.hibernate.generate_statistics=true   # "Session Metrics" block, JDBC statement count
spring.jpa.hibernate.ddl-auto=validate                      # Flyway owns DDL
```

## 5. Known limits (say them honestly)

* With 12 rows PostgreSQL still picks a sequential scan; `idx_job_status_last_date` only pays off on larger tables.
* `@Version` is bumped by Hibernate for entity updates, not for bulk JPQL updates.
* Case-insensitive uniqueness (company name, job title, email) is checked in the service; the DB constraint is case-sensitive.
